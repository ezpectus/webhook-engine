## Защита TASK-005 — ✓ защищена голосом (2026-10-25)

*Юзер подтвердил эталонные ответы («согласен» по S2/S3 + общее
подтверждение). Ответы оставлены как каноничная запись.*

- **S2** ✓ — equal jitter vs full: нижняя граница `d/2` гарантирует,
  что ретрай не случится «слишком рано» — endpoint'у гарантирована
  передышка ≥ половины задержки; full jitter может дать ~0 и добить
  умирающий сервис. При этом разброс [d/2, d) всё ещё размазывает
  стадо. · `BackoffPolicy.cs → ComputeDelay`
- **S3** ✓ — schedule после `SaveChanges`, не до: куча — ускоритель,
  PG — истина. Сначала фиксируем `RetryScheduled+NextAttemptAt`
  durable, потом добавляем в быструю кучу. Обратный порядок даёт
  окно «в куче есть, в PG нет» → при крахе событие потеряно для
  скана — хуже, чем «в PG есть, в куче нет» (доберёт тиком). ·
  `DeliveryWorker.cs`
- **S4** ✓ — рестарт убивает кучу, но не PG: `NextAttemptAt` —
  persistent. Новый процесс на первом же обходе sweeper'а сканирует
  `Status IN (Pending, RetryScheduled)` и `NextAttemptAt <= now` —
  всё due-работа снова в канале. Проверено живьём: хаос #3, ретраи
  продолжились после kill · `SweeperService.cs`
- **S5** ✓ — версии нужны для in-memory корректности *до* PG:
  reschedule бампит версию → старая запись кучи тихо пропускается
  на dequeue. Без версий дубликат в куче выдал бы лишний enqueue
  раньше времени — PG потом разрулит (claim-гард), но это
  бесполезный double-enqueue. Версии — дешёвая фильтрация шума,
  PG — страховка · `HeapRetryScheduler.cs`

## Защита TASK-004 — ✓ подтверждено юзером 2026-10-26

*Эталонные ответы (приняты):*

- **старт-полный** — новый webhook получает всплеск сразу (capacity
  токенов доступно с первого события): первый бурст не ждёт
  накопления. Пустое ведро задержало бы первые события — плохой UX
  для «подключил webhook → пошли события»
- **ленивый refill** — токены начисляются по прошедшему времени при
  каждом вызове, без фонового тика: нет таймера на каждый bucket
  (тысячи вебхуков = тысячи тиков), нет работы когда нет запросов
- **`lock`** — bucket шарится между `WorkerParallelism` воркерами;
  refill + взятие токена — read-modify-write пары `(_lastRefill,
  _tokens)`, без лока два воркера прочтут одно значение и снимут
  токен дважды → уход в минус

## Тренажёр (без единственно верного ответа — по желанию, в любой день)

- **T1** ✓ разобрано (дубль приёма vs отправки; ack после send)
- **T2** ✓ канон (записан 07.11): «ровно-один-раз» на транспорте не
  существует — это свойство **пары**: at-least-once доставка +
  **идемпотентный получатель**. Что должен делать он: durable seen-set
  по стабильному ключу (eventId из тела/подписи), вторая копия → 200
  без сайд-эффекта. Ровно наш dedup, только на его стороне — и те же
  ограничения окна, что в H-1
- **T3** ✓ канон (записан 07.11): потеря — всегда хуже: молчаливое
  враньё, дубль хотя бы обрабатывается получателем. Несимметричность
  осознанная: ingest выбрал «честный отказ» (503/5xx — ни дубль, ни
  потеря, а сигнал ретраить), доставка — дубль (ат-least-once: потеря
  необратима). Единственное место, где мы добровольно «теряем» — сам
  dedup: одинаковое событие внутри окна считается дублем — выбранная
  семантическая потеря ради идемпотентности клиента
- **T4** ✓ разобрано 2026-10-26 — **ответ юзера верный с первого
  раза**: первым ломается in-memory token bucket (каждый инстанс
  держит своё ведро → эффективный лимит = 2× от заданного).
  Дополнение: БД при этом не ломается — она shared truth; далее идут
  чаще гонки В7-типа (два sweeper'а реклеймят одни lease) и
  раздельные `EventQueue` (capacity/backpressure перестаёт быть
  глобальным). Аргумент за Redis-backed лимитер и leader-election
  в scale-волне · `next.md` пункты 1–3
- **T5** ✓ канон (записан 07.11): клиент видит timeout → ретраит →
  мы уже закоммитили → dedup отвечает `duplicate` с тем же eventId
  (Redis-ветка, или 23505 через PG). Система видит: событие принято
  ровно один раз. «Дубль» — это второй HTTP-запрос, не второе событие.
  Опасный вариант — клиент ретраит с **изменённым** payload под тем же
  смыслом → новое событие. Ровно это чинит клиентский Idempotency-Key
  (H-2): ключ выживает мутацию тела
- **T6** ✓ канон (записан 07.11): `MaxAttempts` ограничивает
  **расписания**, а не **отправки**. Каждая отправка, чей send
  переживает lease, может породить параллельную копию — хаос #7:
  3 реальных send'а при attemptCount=2. Худший случай ≈
  `MaxAttempts × (1 + sendDuration/lease)` — при lease 5мин и timeout'ах
  секунд практически MaxAttempts+ε, при lease < send рост линейный.
  Ровно мотивация lease-versioning (H-3): писать ack только под
  своей версией claim'а
- **T7** ✓ канон (записан 07.11): 429 получателя — истина о **его**
  ёмкости, наш лимитер — только вежливость и контроль расхода.
  Расходятся: наш жёстче → недоиспользуем канал (безопасно, медленнее);
  их жёстче → 429 = retryable с их `Retry-After`, отступаем ниже
  своего bucket'а. Наш лимитер формирует поток, их 429 его корректирует.
  Идеал — адаптив: их 429 снижает наш permits/sec до их реального
  потолка (scale-волна)
