# Backlog — тикеты

Задачи выдаёт Devin в формате тикетов (как техлид в команде), выполняет юзер.
Платформа (зона Devin) делается по явному запросу отдельно от этих тикетов.

**Статусы:** `todo` → `in-progress` → `review` → `done`.
`done` ставится только после checkpoint-вопросов (см. AGENTS.md).
Статус в тикете обновляет юзер при смене этапа.

**Формат тикета:** контекст (зачем это системе) → что сделать →
acceptance criteria → вопросы на понимание.

**Размеры:** XS < 1ч · S ~вечер · M ~2–3 вечера · L ~неделя.

## TASK-002 · Idempotency: dedup на приёме через Redis

**Стадия:** 2 · **Зона:** ядро · **Размер:** M ·
**Зависит от:** TASK-001, P-01, P-03 · **Статус:** `todo`

**Контекст.** Клиенты и сеть ретраят запросы — одно и то же событие может
прилететь дважды. Приём должен быть идемпотентным: повтор того же события
не создаёт вторую доставку.

**Что сделать.** SHA256-ключ события (решить, что входит в хеш: тело?
webhook id? заголовки?) → `SET NX` в Redis с TTL = окно дедупликации.
Решить, что отвечать клиенту на дубль (200 с тем же event id? 409?).

**Acceptance criteria:**
- [ ] Повторный POST идентичного события не порождает вторую запись
- [ ] TTL окна — конфигурируемый параметр
- [ ] Решение про ответ на дубль записано в журнал решений PLAN.md

**Вопросы на понимание:** событие пришло повторно *после* истечения окна —
это дубль или новое событие? Почему это допустимо? Что будет, если Redis
недоступен в момент проверки — фейлим приём или пропускаем без dedup?

## TASK-003 · Очередь: bounded channel и backpressure-политика

**Стадия:** 3 · **Зона:** ядро · **Размер:** M ·
**Зависит от:** TASK-001, P-01 · **Статус:** `todo`

**Контекст.** Пиковая нагрузка — ~1M событий/сек. Если лить всё в память
без ограничений — OOM и смерть процесса. Нужен bounded `Channel` и
честная политика: что делаем, когда очередь полна.

**Что сделать.** Bounded channel между приёмом и воркерами. Выбрать
политику переполнения: reject (503 + Retry-After), block producer,
drop — и обосновать выбор именно для webhook-доставки.

**Acceptance criteria:**
- [ ] Поведение при полной очереди детерминировано и задокументировано
- [ ] Есть счётчик отказов (метрика backpressure)
- [ ] Выбор политики обоснован в журнале решений

**Вопросы на понимание:** почему drop-oldest здесь хуже reject?
Что видит клиент при переполнении и как это влияет на гарантию?

## TASK-005 · Retry scheduler: min-heap + backoff/jitter

**Стадия:** 5 · **Зона:** ядро · **Размер:** L ·
**Зависит от:** TASK-003, P-04 · **Статус:** `todo`

**Контекст.** Упавший endpoint нельзя долбить сразу — только хуже.
Нужны отложенные ретраи: экспоненциальный backoff, jitter против
thundering herd, потолок попыток → DLQ.

**Что сделать.** Min-heap отложенных отправок по `nextAttemptAt`.
Формула задержки `base * 2^attempt ± jitter`, max attempts → DLQ.
Воркер-тикер, доставающий due-элементы.

**Acceptance criteria:**
- [ ] Извлечение ближайшего due — O(log n) через heap
- [ ] Jitter реально размазывает ретраи (проверить замером/тестом)
- [ ] После max attempts событие уходит в DLQ, не теряется

**Вопросы на понимание:** почему без jitter все ретраи одной пачки
сходятся в одну секунду? Какие ошибки ретраить бессмысленно (4xx?)?

## TASK-006 · DLQ: семантика и replay

**Стадия:** 6 · **Зона:** ядро · **Размер:** M ·
**Зависит от:** TASK-005, P-02 · **Статус:** `todo`

**Контекст.** События, исчерпавшие ретраи, нельзя терять и нельзя
крутить бесконечно. DLQ — «карантин» для ручного разбора.

**Что сделать.** Условия попадания в DLQ (исчерпаны ретраи, неретраябельная
ошибка, невалидный payload). Replay: как событие возвращается в поток —
в очередь с нулевым счётчиком попыток или с сохранением истории?
Как replay проходит dedup?

**Acceptance criteria:**
- [ ] Правила «что уходит в DLQ» зафиксированы в PLAN.md
- [ ] Replay не теряет событие и не вводит недопустимых дублей
- [ ] Из DLQ можно ответить «почему это событие здесь» (причина, история)

**Вопросы на понимание:** replay после фикса endpoint'а — это дубль для
клиента? Почему в DLQ обязательно хранить причину, а не только payload?
