# Backlog — тикеты

Задачи выдаёт Devin в формате тикетов (как техлид в команде), выполняет юзер.
Платформа (зона Devin) делается по явному запросу отдельно от этих тикетов.

**Статусы:** `todo` → `in-progress` → `review` → `done`.
`done` ставится только после checkpoint-вопросов (см. AGENTS.md).
Статус в тикете обновляет юзер при смене этапа.

**Как работать с тикетом:**
1. Прочитать «Контекст» — зачем это системе.
2. **Сначала** ответить на пункт «Решения принять до кода» — записать
   ответы в `PLAN.md` (журнал решений). Это и есть планирование.
3. Писать код в указанном месте. Застрял → лесенка помощи (AGENTS.md #8).
4. Проверить по «Проверка», прогнать AC, перевести статус в `review`.
5. Ответить на checkpoint-вопросы → `done`.

**Размеры:** XS < 1ч · S ~вечер · M ~2–3 вечера · L ~неделя.

Защита подтверждена голосом 2026-10-26 (старт-полный / ленивый

**Контекст.** Сторонние API банят за превышение RPS. Лимит per-endpoint;
превышение откладывает отправку, не дропает.

**Решения принять до кода:**

  берутся (`WebhookEndpoint.RateLimitPerSecond` уже есть в схеме)
- Состояние bucket'а: in-memory `ConcurrentDictionary<Guid, Bucket>`
  vs Redis — что при двух инстансах приложения?
- Что делает воркер, когда `AcquireDelayAsync` вернул >0: спит?
  переqueues событие? (связь с retry-scheduler — общий механизм
  отложенной отправки?)

**Контракт/место:** реализовать `IWebhookRateLimiter`
(`Core/Abstractions/IWebhookRateLimiter.cs`), например
`Infrastructure/RateLimiting/TokenBucketRateLimiter.cs` + сам bucket
в `Core` (чистый алгоритм — юнит-тестируемо без инфраструктуры).

**Acceptance criteria:**
- [ ] Исчерпание токенов → откладывание, событие не теряется
- [ ] Лимиты конфигурируемы per webhook

**Проверка:** юнит-тест: burst=10 rps=5 → первые 10 сразу, 11-й ~через
200мс; интеграция: webhook с limit=2, отправить 5 событий →
замерить интервалы.

**Вопросы на понимание:** token bucket vs leaky bucket — почему для
внешних API обычно первый? Что даёт capacity (допустимый всплеск)?

### Путь реализации (подсказки, не код)

Скелет ждёт: `src/WebhookEngine.Core/RateLimiting/TokenBucket.cs`,
тесты — `tests/.../TokenBucketTests.cs` (пустые Fact — заполнить самому).

1. **Состояние:** `_capacity`, `_refillPerSecond`, `_tokens`,
   `_lastRefill`. Пополнение — ленивое: считаем по прошедшему времени
   при каждом вызове, а не тикаем таймером.
2. **Время — снаружи.** Не зови `DateTimeOffset.UtcNow` внутри класса —
   принимай `TimeProvider` в конструктор (дефолт `TimeProvider.System`).
   Иначе тесты будут ждать реальные секунды.
3. **TryTake:** refill → `tokens >= 1` → `tokens--`, true; иначе false.
4. **TimeUntilAvailable:** refill → `tokens >= 1 ? Zero : (1-tokens)/rate`.
5. **Подумай до кода:** нужен ли `lock` (несколько воркеров дергают один
   bucket)? что при `refillPerSecond <= 0`? может ли `tokens` уйти в минус?
6. После чистого bucket — обёртка `IWebhookRateLimiter` поверх
   `ConcurrentDictionary<Guid, TokenBucket>` (per-webhook состояние,
   MVP — память; Redis-версия только при втором инстансе, D6).
7. Врезка в воркер — после того как класс работает: limiter говорит
   «жди 200мс» → событие уходит в отложенную отправку, общий механизм
   с ретраем (D7).

**Баги, которые поймаю на ревью** (не подглядывай — сам подумай):
отрицательные токены при параллельном доступе; refill без `min(cap)`;
тесты, зависящие от реального времени (флаки).

### H-2 · Клиентский `Idempotency-Key` header · `todo` · S–M

**Проблема:** content-hash не различает «ретрай того же запроса» и
«новое событие с тем же телом». Клиенту с собственными event id
нельзя положиться на hash тела (как у Stripe — ключ придумывает клиент).

**Что сделать:** `POST /events` принимает header `Idempotency-Key`.
Если есть → ключ = `sha256(webhookId + ":" + header)` (тело не
участвует — клиент владеет идемпотентностью). Нет → fallback на
content-hash как сейчас.

**Подумай до кода:**
- лимит длины header'а? (256 символов — разумно)
- одинаковый ключ + разное тело — что возвращать? (у Stripe — ошибка
  `422 idempotency_key_in_use`; у нас можно `409` или `duplicate`)

**Ловушка:** если тело не участвует вообще, `key=K, body=A` → принято,
потом `key=K, body=B` → молча «duplicate», и B потерян для клиента.
Храни рядом с ключом хеш первого тела и сравнивай.

**AC:** тот же header + то же тело → `200 duplicate` с исходным id;
тот же header + другое тело → `409`/`422` (не duplicate!) — решение
зафиксируй в PLAN журнале; два разных header'а с одним телом → два
события.

### H-3 · Lease-version claim (починка В7) · `todo` · M

**Проблема:** медленный канал > 5 мин lease → sweeper реклеймит
InFlight → второй воркер шлёт параллельно с первым; `AttemptCount`
пишется last-write-wins — теряется инкремент. Дубль легален, но
счётчик врёт.

**Что сделать:** колонка `ClaimVersion int` на `notification_events`.
Атомарный claim → `ClaimVersion++`. Воркер пишет результат только
`WHERE ClaimVersion = <его версия>` — не совпало → его claim протух,
значит sweeper уже перехватил событие → просто бросить элемент.
Update стал optimistic-concurrency guard'ом.

**Подумай до кода:**
