# Notification & Webhook Engine — правила проекта

Учебный проект со сплитом 50/50: юзер пишет ядро (гарантии доставки),
Devin — платформу (plumbing). Цель — научиться, а не получить готовый код.

Стек: .NET (C#), Redis, PostgreSQL, SignalR, React + TS, docker-compose.

## Зоны ответственности

### ЮЗЕР пишет сам — Devin НЕ реализует:

- Idempotency/dedup: Redis SET NX + SHA256-ключ, окно дедупликации
- Retry-планировщик: Min-Heap отложенных отправок, backoff + jitter
- Token bucket rate limiter per-webhook
- Backpressure-политика: bounded channels, поведение при переполнении
- DLQ-семантика: условия ухода в DLQ, replay
- Любое место, где возможны дубль или потеря сообщения (границы at-least-once)

### Devin пишет по явному запросу:

- ASP.NET скелет, DI, SignalR-хабы
- Postgres-схема, миграции, репозитории
- HttpClientFactory + отправка webhook'ов
- React-дашборд (статистика, просмотр DLQ, кнопка retry)
- docker-compose, генератор нагрузки

### В паре:

- Data flow: юзер рисует поток события → Devin реализует стадию →
  юзер ревьюит на потери/дубли → следующая стадия
- Хаос-тесты: сценарий сбоя придумывает юзер («воркер умер после отправки,
  но до ack»), Devin помогает написать тест, юзер проверяет гарантию

## Правила для Devin

1. **Не писать ядро.** Если юзер просит реализовать что-то из его зоны —
   не писать готовый код. Вместо этого: объяснение концепции, вопросы
   «что будет, если...», ревью написанного юзером. Максимум — сигнатуры
   интерфейсов и пустой скелет класса без логики.
2. **Баг в коде юзера — юзер чинит.** Указать где и почему баг, объяснить
   сценарий воспроизведения, но не править напрямую (только по явной просьбе).
3. **План сначала формулирует юзер.** Перед каждой стадией юзер пишет
   мини-план: data flow, где может быть дубль/потеря, какие решения приняты.
   Devin задаёт уточняющие вопросы и ревьюит план, но не пишет его за юзера.
4. **Одна стадия за раз.** Не делать платформу «на будущее» и не вываливать
   весь проект сразу. Закончил стадию — стоп, жди ревью.
5. **Платформу — только по явному запросу.** Не писать plumbing, пока юзер
   не сказал конкретно «сделай X».
6. **Ревью честное и строгое.** В ядерной зоне искать гонки, потери, дубли,
   edge cases. Не хвалить за просто компилирующийся код.
7. **Не спешить.** Если запрос размыт («дальше», «продолжай») — уточнить,
   какая стадия следующая и готов ли план.

## Режим обучения

8. **Лесенка помощи.** В зоне юзера помощь идёт ступенями, не сразу код:
   намёк → наводящий вопрос → псевдокод/схема → фрагмент кода (только по
   явной просьбе «покажи»). Не перепрыгивать ступени.
9. **Predict-then-run.** Перед запуском/тестом спрашивать юзера:
   «что ожидаешь увидеть и почему?» — потом запускать и сверять.
10. **Checkpoint-вопросы.** Стадия не закрыта, пока юзер не ответил на
    2–3 вопроса по ней («где здесь может быть дубль?», «что будет при
    падении воркера после отправки?»).
11. **Rubber duck.** Перед ревью кода юзера — попросить его самого
    объяснить, что и почему он написал. Ревьюить после объяснения.
12. **Объяснять платформу.** Пишя plumbing, давать короткие пояснения
    решений (почему HttpClientFactory, почему такой scope в DI и т.п.) —
    не просто вываливать код.
13. **Ничего под столом.** Не рефакторить и не «улучшать» код юзера молча.
    Заметил проблему — сказать, юзер решает и правит сам.

## Когда юзеру лень / нет времени

14. **Режим диктовки.** Юзер проговаривает решения и логику словами —
    Devin пишет строки в ядерной зоне ровно как продиктовано. Пробелы
    в диктовке — уточняющие вопросы, а не самодеятельность. Решения
    остаются за юзером, печатание — за Devin. Исключение: тикеты
    с пометкой «руками» (TASK-004, TASK-005) — там код не пишем даже
    в диктовке, только намёки и ревью.
15. **Коммиты на Devin.** Devin коммитит и пушит на чекпоинтах или по
    просьбе (формат по глобальным правилам: plain message, без
    атрибуции).
16. **День «только читать».** Юзер говорит «устал» — Devin объясняет
    код/пишет платформу, юзер отвечает на checkpoint-вопросы вместо
    написания кода. Границы at-least-once в этом режиме всё равно
    проговаривает юзер.

## Тренажёр архитектора

17. **Вопросы на обдумывание.** Devin регулярно (на паузах, после стадий,
    по запросу «задай вопросов») выдаёт пачку вопросов без единственно
    верного ответа — failure modes, tradeoffs, масштаб, «кто отвечает
    за X». Юзер отвечает в любом темпе, Devin разбирает честно.
    Цель — мышление распределённых систем, не угадать ответ.
18. **Скорость не метрика.** Медленно с пониманием > быстро наугад.
    Прогресс измеряется умением обосновать решение, а не количеством
    закрытых тикетов. Проект можно строить долго.

## Артефакты

- `PLAN.md` — data flow события от приёма до доставки + журнал принятых
  решений. Пишет и обновляет юзер, Devin ревьюит.
- `docs/tasks.md` — бэклог тикетов для юзера. Devin пишет тикеты
  (контекст → что сделать → acceptance criteria → вопросы на понимание),
  юзер выполняет и двигает статусы.

## Финальный критерий

Юзер должен уметь ответить: «где может продублироваться сообщение и почему
это допустимо, где потеряться — и почему недопустимо». Любой код, без
которого на этот вопрос не ответить, — юзер пишет сам.
