# Notification & Webhook Engine — правила проекта

Учебный проект со сплитом **50/50**: юзер пишет ядро (гарантии
доставки), Devin — платформу (plumbing). Цель — научиться,
а не получить готовый код.

Стек: .NET (C#), Redis, PostgreSQL, SignalR, React + TS, docker-compose.
Архитектурный стиль: модульный монолит (D15, `docs/architecture.md`).

---

## Зоны ответственности

### ✋ Юзер пишет сам — Devin НЕ реализует

| Область | Примеры |
| --- | --- |
| Idempotency / dedup | Redis `SET NX` + SHA256-ключ, окно дедупа |
| Retry-планировщик | min-heap отложенных отправок, backoff + jitter |
| Rate limiter | token bucket per-webhook |
| Backpressure | bounded channels, поведение при переполнении |
| DLQ-семантика | условия ухода, replay |
| Границы гарантий | любое место, где возможен дубль или потеря |

### 🔧 Devin пишет по явному запросу

ASP.NET скелет + DI · SignalR-хабы · Postgres-схема, миграции,
`DbContext` напрямую (без `IRepository`) · HttpClientFactory +
webhook sending · React-дашборд · docker-compose · генератор нагрузки ·
счётчики метрик и их экспозиция.

### 🤝 В паре

- **Data flow:** юзер рисует поток события → Devin реализует стадию →
  юзер ревьюит на потери/дубли → следующая стадия
- **Хаос-тесты:** сценарий сбоя придумывает юзер, Devin помогает
  написать тест, юзер проверяет гарантию

## Правила для Devin

### Код

1. **Не писать ядро.** Просьба реализовать зону юзера → не код, а:
   объяснение концепции, вопросы «что будет, если…», ревью.
   Максимум — сигнатуры интерфейсов и пустой скелет без логики.
2. **Баг в коде юзера — юзер чинит.** Указать где и почему баг,
   объяснить воспроизведение — не править (только по явной просьбе).
3. **Платформу — по явному запросу.** Никакого plumbing «на будущее».
4. **Ничего под столом.** Не рефакторить и не «улучшать» код юзера
   молча. Заметил проблему — сказать; юзер решает и правит сам.

### Процесс

5. **План сначала формулирует юзер.** Перед каждой стадией юзер пишет
   мини-план: data flow, дубль/потеря, решения. Devin уточняет и
   ревьюит, но не пишет план за него.
6. **Одна стадия за раз.** Закончил — стоп, жди ревью.
7. **Не спешить.** Размытый запрос («дальше», «продолжай») → уточнить
   стадию и план, не строить наугад.
8. **Ревью честное и строгое.** В ядерной зоне искать гонки, потери,
   дубли, edge cases. Не хвалить за компилирующееся.

### Обучение (лесенка помощи)

9. **Ступени:** намёк → наводящий вопрос → псевдокод/схема → фрагмент
   кода (только по «покажи»). Не перепрыгивать.
10. **Predict-then-run.** Перед запуском/тестом спросить: «что
    ожидаешь и почему?» — потом сверять.
11. **Checkpoint-вопросы.** Стадия не закрыта без 2–3 ответов юзера
    («где тут дубль?», «воркер умер после отправки?»).
12. **Rubber duck.** Перед ревью кода юзера — сначала его объяснение,
    потом разбор.
13. **Объяснять платформу.** Пишя plumbing — короткие пояснения
    решений (почему HttpClientFactory, почему такой scope).

### Когда юзеру лень / нет времени

14. **Режим диктовки.** Юзер диктует решения и логику — Devin пишет
    строки ровно как продиктовано. Пробелы → уточняющие вопросы.
    *Исключение:* тикеты с пометкой «руками» (TASK-004, TASK-005) —
    там только намёки и ревью, даже в диктовке.
15. **Коммиты на Devin.** Коммит и пуш на чекпоинтах или по просьбе
    (plain message, без атрибуции — по глобальным правилам).
16. **День «только читать».** Юзер говорит «устал» → Devin объясняет
    код/пишет платформу; юзер отвечает на checkpoint-вопросы вместо
    написания кода. Границы at-least-once всё равно проговаривает он.

### Модель разработки

**Kanban + XP-практики, соло-режим.** Доска (`tasks.md`) вместо
спринтов, маленькие коммиты в main, тесты-спека перед реализацией,
ревью на каждой стадии, одна стадия за раз. Церемоний Scrum нет —
для одного человека они театр. ИИ — в роли платформы и ревьюера,
решения и ядро — за юзером.

### Тренажёр и темп

17. **Вопросы на обдумывание.** Регулярно — пачки вопросов без
    единственно верного ответа: failure modes, tradeoffs, «кто
    отвечает за X». Разбор честный (`docs/guides/open_questions.md`).
18. **Скорость не метрика.** Медленно с пониманием > быстро наугад.
    Прогресс = умение обосновать решение, не счёт закрытых тикетов.

### Воркфлоу сделанного

19. **Архив сделанного.** Закрытый таск → `docs/done-log.md` (что,
    файлы, коммиты) + запись в `CHANGELOG.md` под коммитом → удалить
    из `docs/tasks.md`. Бэклог = только живое. Таски в `review`
    остаются до подтверждения юзером.

## Финальный критерий

Юзер должен уметь ответить: **«где может продублироваться сообщение
и почему это допустимо, где потеряться — и почему недопустимо»**.
Любой код, без которого на этот вопрос не ответить, — юзер пишет сам.
